What I learned moving CSP into a custom plugin on managed hosting

April 15, 2026 · 9 min read WordPress Security CSP

In this post

  1. Why CSP got messy
  2. Three competing sources
  3. The fix: one source of truth
  4. Takeaways

If you're running WordPress on managed hosting with a bundled WAF, you've probably hit the same wall I did: three different layers all trying to set your Content-Security-Policy header, none of them aware of the others. Here's what I found, and how I made it stop.

Why CSP got messy

I run courtneyr.dev on GoDaddy Managed WordPress, which bundles Sucuri WAF at the edge. I also use the HTTP Headers plugin, plus a small custom plugin for font-display swap and a few other performance tweaks. None of these layers know about each other.

The result: my CSP was being set three times. Whichever layer was last to write the response header won, and which one that was depended on caching state, time of day, and what I'd had for breakfast.

Note

If you're seeing inconsistent Content-Security-Policy values across page loads, this is a classic sign of competing header sources. Don't assume one plugin is “wrong” — they may all be right, and the problem is that there's more than one of them.

Three competing sources

Auditing live headers with curl -I made the picture clear:

$ curl -sI https://courtneyr.dev/ | grep -i csp
content-security-policy: default-src 'self'; ...   # source 1
content-security-policy: default-src *; ...        # source 2 (??)

The three sources, in priority order from the edge inward:

  1. Sucuri WAF — adds “Additional Security Headers” at the edge, overrides anything below.
  2. Sucuri WordPress plugin — adds headers at the application layer.
  3. HTTP Headers plugin — adds more headers at the application layer.

Plus my custom font-display-swap-site-performance-security plugin, which I wanted to take over CSP entirely.

The fix: one source of truth

The plan was simple, the execution less so. I wanted CSP to live in exactly one place: my custom plugin's send_headers hook. Everything else needed to stop trying.

Step 1: clear the WAF

This required Sucuri support. Their team (shoutout to Dobromir) disabled the WAF-level “Additional Security Headers” feature for my account. I cannot stress enough that this is something you have to ask for — you can't toggle it from the plugin GUI.

Step 2: disable plugin-level CSP

In the Sucuri plugin's Headers Management page (admin.php?page=sucuriscan_headers_management), I unchecked CSP. Same in HTTP Headers plugin settings.

Step 3: add CSP to the custom plugin

add_action( 'send_headers', function() {
    if ( is_admin() ) return;
    $csp = "default-src 'self'; "
         . "script-src 'self' 'unsafe-inline' s.ytimg.com www.googletagmanager.com; "
         . "style-src 'self' 'unsafe-inline' fonts.googleapis.com; "
         . "font-src 'self' fonts.gstatic.com; "
         . "img-src 'self' data: https:; "
         . "connect-src 'self' region1.google-analytics.com analytics.google.com; "
         . "frame-src https:; ";
    header( 'Content-Security-Policy-Report-Only: ' . $csp );
}, 100 );

Note the Report-Only directive. I'm not enforcing yet — I want to see what breaks before I do.

Takeaways

  • On managed hosting, always audit live headers with curl before assuming plugin settings are taking effect.
  • Verify cache freshness with x-sucuri-cache: MISS and x-gateway-cache-status: MISS before drawing conclusions.
  • The WAF will silently override application-layer plugin settings. Plugin CSP only works reliably when the WAF is cleared.
  • One source of truth, in code I control, version-tracked in Git. Everything else is a future debugging nightmare.
